# Security review — 12 September 2026

This review examined the implemented API, OAuth/session flows, owner authorization, source HTTP clients, email interpretation, People provider boundaries, native storage/link handling, deployment configuration, and backup helper. It combines code inspection and targeted regression tests; it is not an independent penetration test or a claim that no vulnerabilities remain. The two assembled debugging passes are recorded separately in TEST_RESULTS and BUILD_STATUS.

## Concrete findings and fixes

| Finding | Change and evidence |
| --- | --- |
| Backup database URL query options were dropped, including explicit TLS verification; inherited libpq variables could override the destination. | `scripts/backup.py` maps supported TLS/connection options to libpq variables, rejects duplicated or unsupported options, and removes inherited `PG*` settings before building the explicit connection. Tests exercise verified TLS preservation, host/service override rejection and ambiguous options. |
| `pg_restore --dbname` accepts a connection string, so a percent-decoded database component could bypass the intended restore destination/name guard. Raw URL comparison also missed host aliases. | Only simple database names are accepted; restore requires an explicitly configured source and a different decoded target database name ending `_restore`, even for different hostnames. Regression cases include encoded connection strings and URI-shaped database names. This is a guard against accidental/ambiguous targeting, not protection from a hostile operating-system administrator. |
| A failed `pg_dump` could leave a partial restic snapshot even after the old pipe's exit-code check reported failure. Database passwords were passed in child environments. | Restic now invokes `pg_dump` using `--stdin-from-command`, which cancels snapshot creation on command failure. Database credentials use a mode-0600 temporary pgpass file removed on exit; no plaintext database dump is written. Restore checks repository integrity before streaming and validates snapshot arguments. Subprocess orchestration and private-file cleanup are tested; actual restic/off-server operation remains unverified. |
| Settings errors or object representations could expose configuration input; callback settings allowed unexpected origins. | Sensitive fields are omitted from representations and validation error input. Public URL must be a plain HTTP(S) origin; nonlocal OAuth callbacks must use the configured HTTPS origin without credentials, query, or fragment. Regressions cover secret redaction and rejected callback/origin variants. |
| OAuth callback exchange reconstructed its URL from incoming request host/scheme, which is unreliable behind a reverse proxy and permits host-header influence. | Both sign-in and Gmail callbacks now use their configured redirect URI plus the received query. Root-owned callback tests exercise the configured HTTPS origin despite hostile/inaccurate request origin. |
| Pending login limits were keyed only by caller-supplied device UUID, and API request bodies lacked an application-level limit. | A bounded rolling auth-request limiter applies to the single API process, using the request peer rather than directly reading forwarding headers, with an additional process-wide ceiling. A 4 MiB limit checks both declared and streamed bodies. Tests cover rotating forwarded addresses, peer/global limits, expiration and streamed/declaration overflow. |
| Email quotations/forwarded nested MIME could be interpreted as current status; malformed or oversized MIME could interrupt processing. Sender-to-employer association was independent of message matching. | The email owner added bounded MIME parsing, quotation removal, attached/forwarded-message exclusion, explicit content issues and conservative sender screening. Automatic updates require separate message identity, status meaning and sender trust gates; ambiguous, unauthenticated or unassociated messages become review items. Header trust limitations remain below. |
| Source aliases did not consistently preserve registry identity, which would reject university/JobSpy candidates during ingestion. USAJOBS configuration ignored dotenv-loaded Settings. | Factory, candidate, normalized job and health source identity now agree, JobSpy preserves the registered tenant, and USAJOBS reads validated Settings with explicit override support. Regression tests cover both integration failures. These are correctness findings relevant to trustworthy evidence, not authorization bypasses. |

The backup changes follow the documented behavior of [PostgreSQL restore connection strings](https://www.postgresql.org/docs/current/app-pgrestore.html), [libpq environment and password guidance](https://www.postgresql.org/docs/current/libpq-envars.html), and [restic command-input backups](https://restic.readthedocs.io/en/stable/040_backup.html#reading-data-from-a-command).

## Controls inspected

- OAuth uses fixed Google endpoints, RS256 verification against Google keys, issuer/audience/expiry checks, server-side state, nonce and PKCE verification. Device challenge redemption is one-time and bound to the initiating device. Owner enrollment is serialized and restricted to the configured owner; subsequent identity binds to Google subject. Refresh token replay revokes sessions for that device. Provider tokens are encrypted at rest; session tokens are stored hashed. Existing provider and PostgreSQL tests cover these contracts; real Google consent still requires credentials.
- Owner-facing API routes depend on authentication and scope record access to the owner. Error handlers redact request input and raw provider failures; callback responses use no-store/no-referrer. No email or Slack messages were sent as part of this review.
- Job source HTTP uses a bounded resolver and connection timeouts, rejects nonpublic and mixed DNS answers, pins the checked address to the socket, verifies TLS against the original hostname, revalidates redirects, strips cross-origin credentials, prohibits HTTPS downgrades and limits response bytes/retries. This blocks private/metadata destinations without disabling TLS checks. LinkedIn job sourcing remains disabled. Source HTML is reduced to readable text or sanitized formatting; external content is evidence, never executable instructions.
- Gmail/Google and the configured People search provider use fixed HTTPS endpoints. Credentials are optional and independent. JobSpy remains disabled unless explicitly installed/enabled, restricted to the selected allowlisted site, isolated from application secrets and bounded by subprocess/runtime/output limits. It cannot certify a complete job description or employer eligibility.
- Production Compose exposes Caddy's public HTTP/HTTPS ports; PostgreSQL/Redis remain internal. The backend runs as a nonroot user with dropped capabilities/no-new-privileges. Images and CI actions are pinned. These are configuration inspections, not a deployed-host firewall or container escape test.
- The native owner reports encrypted SQLite with runtime cipher verification, OS secure storage for keys/tokens, account/API-origin/demo-scoped caches, logout and asynchronous-result generation guards, atomic snapshot replacement, revision-aware idempotent offline writes, strict internal deep links and server-authoritative notification destinations. External links permit HTTP(S) without URL credentials; remote API origins require HTTPS. Android release cleartext and backup are disabled; missing signing credentials do not fall back to a debug key. Windows installer scope is per-user; there is no automatic downloaded-code execution. Native results and platform limitations are maintained in the client test/build records.

## Verification and remaining limits

The latest focused command ran `test_security_review.py`, `test_config.py`, `test_http_contract.py` and `test_connectors.py`: **82 passed**, with three upstream HTTPX/Starlette/Authlib deprecation warnings. Scoped Ruff checks and formatting passed for modified files. Earlier SafeHTTP regression tests separately passed; the full assembled runs must include them again. Tests with mocked provider or subprocess boundaries demonstrate application behavior, not live provider identity, backup recoverability or deployed TLS.

The following remain genuine qualification items:

1. Restic is unavailable here and no protected off-server repository was configured. Run an encrypted backup and clean restore drill with real PostgreSQL, compare invariant records and preserve an independently protected encryption key before relying on disaster recovery. Review existing snapshots created by older pipe-based tooling; code changes do not certify old backups.
2. Google/Gmail authentication, DMARC-like screening and employer association remain distinct. Gmail payload headers are used conservatively: exactly one Google authentication-results header, aligned DMARC pass and either an official employer domain or previously reviewed exact sender are required. This is not independent cryptographic DKIM validation and cannot prove authenticity of imported mailbox messages or protect against a compromised employer/mailbox account. Such provenance concerns require review; a matching subject/body alone cannot authorize an automatic update.
3. The baseline rate limiter is in-memory and per API process. Multiple API replicas require shared or edge rate limiting; restart clears its windows. The normal user/session/device checks remain necessary. Reverse-proxy trust must be configured narrowly at deployment.
4. Source network access in this workspace cannot use production public DNS: the actual safe runtime smoke returned `DNS_UNAVAILABLE`. Public feasibility evidence was collected separately through the managed egress path and does not prove the production connector transport works on a target VPS. JobSpy upstream network behavior, tenant-specific Workday semantics and employer/E-Verify evidence still require documented independent qualification.
5. Live Google credentials, FCM device delivery, Windows/Samsung secure storage behavior, signed installers/APKs, platform upgrade behavior and deployed TLS are not verified by Linux unit tests. Release artifacts and checksums must be verified through a trusted distribution channel before manual installation.
6. Fixed-endpoint provider clients also depend on upstream library behavior and provider response bounds. Credentialed endpoint behavior and high-volume resource exhaustion have not undergone load testing. Dependency audit outputs are reported separately; a passing scan does not establish absence of vulnerabilities.

No credentials were invented, production accounts enrolled, paid services purchased, protection bypassed, backup repository initialized, or external deployment performed for this review.
